# OOXML Geometry Source Contract

This directory contains the pinned source contract, compiler/evaluator, SVG path emitter, and
production-subset gates for the spec-compiled preset geometry engine. The build-time modules are
development tooling. The generator writes an
explicit 29-definition production subset consumed by `src/shapes/ooxmlGeometryRuntime.ts`: all 28
zero-adjustment flowchart shapes in IDs 61-88 plus bounded-adjustment `donut`. Every other shape
uses the handwritten implementation in `src/shapes/presets.ts`.

The archive, generated catalog, and generation code are excluded from the published npm

## Commands

```bash
pnpm geometry:generate  # validate source and regenerate the deterministic catalog
pnpm geometry:check     # fail when hashes, validation, or generated bytes differ
```

The generated catalog is a development inventory and compiler gate. It records each shape's
guide count, operators, path count, path commands, fill/stroke metadata, handles, connection
sites, and text-rectangle presence. It fingerprints the complete plain-data IR and emitted SVG path
data, and confirms that all unique definitions evaluate at square, wide, and tall extents. The catalog is not
bundled into the renderer. The same command generates
`src/shapes/generated/ooxmlPresetGeometrySubset.ts`; both generated outputs are checked for byte
drift. Generated files are excluded from Prettier so `geometry:generate` remains their only
byte-format authority.

Current pinned-source inventory:

- 187 top-level source entries and 186 unique shape names
- one structurally identical duplicate entry: `upDownArrow`
- 3,910 guide formulas after duplicate-shape collapse
- 319 paths across unique shapes; 63 shapes contain multiple paths
- 12 ordered guide-name rebindings
- eight explicitly registered trailing-zero formula normalizations
- all 17 ECMA guide formula operators represented

## Validation and reconciliation rules

The validator rejects malformed XML, source hash drift, unknown formula operators, wrong
arity, forward or unresolved guide references, wrong DrawingML namespaces, empty paths,
invalid path fill/stroke values, malformed path-command point counts or attributes,
non-equivalent duplicate shape entries, and stale reconciliation records.

Guide formulas are evaluated in document order. Repeating a guide name therefore means
ordered rebinding; it is retained and reported instead of being collapsed. The duplicated
`upDownArrow` elements are structurally equivalent, so the catalog retains the first and
reports the duplicate.

`source-reconciliation.json` is the only place where a pinned-source anomaly can be
normalized. The validator rejects every active `override`, including entries with plausible-looking
URLs, hashes, and case IDs. Supporting an alternative source requires an offline verifier that reads
its bytes, verifies the hash and shape definition, and resolves native PowerPoint oracle metadata.
`manualReferences` are comparison notes; CI checks their field
shape but does not treat them as verified source or oracle evidence.

The current ECMA addendum omits `upArrow`. Its status remains
`pending-native-oracle`; the validator does not choose a replacement definition.

Eight circular-arrow formulas contain an extra fourth trailing `0`. The strict parser still
requires three operands for `+-`; only the eight exact shape/guide/formula tuples in the
reconciliation file are normalized.

## Formula evaluator and numeric contract

`formula-contract.mjs` locks operand order and arity for all 17 operators.
`formula-evaluator.mjs` implements that contract with 60,000ths of a degree for angles and
IEEE-754 binary64 intermediates, without intermediate rounding. For PowerPoint compatibility,
`sqrt x` means `sqrt(abs(x))`, and `at2 0 0` resolves to zero. Division by zero and any
non-finite result are evaluation errors. Negative zero is canonicalized to zero so generated
data stays deterministic. Coordinate formatting and rounding belong to the later path emitter.
The `mod`, `sqrt`, trigonometric-angle, and `at2` compatibility behaviors link directly to
[Microsoft's implementation notes](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oi29500/851cc3e8-ab22-4f5e-86d1-23b0b06d5edd)
inside the generated contract.

The contract includes the predefined guides listed by ECMA plus `cd3`, `hd10`, `wd12`, and
`wd32`, which are used by the official electronic addendum. These four compatibility guides
are derived in the same way as the corresponding circle/height/width fractions.

## Geometry IR

`geometry-ir.mjs` compiles the pinned XML into plain data. The IR preserves ordered adjustment
and calculated guides, including rebinding; XY/polar adjustment handles; connection sites; text
rectangles; path coordinate spaces; fill/stroke/extrusion metadata; and move, line, quadratic,
cubic, arc, and close commands. It contains no DOM, SVG, theme, renderer, or resource-lifecycle
objects.

`evaluatePresetShape()` accepts positive width/height values plus optional named adjustment
overrides. It evaluates adjustment defaults and calculated guides in document order, then
resolves all geometry references. Unknown adjustments, missing guides, invalid extents, zero
divisors, and non-finite results fail with shape/guide context.

The current unique-shape IR contains 298 adjustment guides, 3,612 calculated guides, 241
adjustment handles, 856 connection sites, 181 text rectangles, 319 paths, and 2,907 path
commands. `geometry:check` compiles all 186 shapes and evaluates them at 216x216, 400x180, and
180x400.

## SVG path emission

`path-emitter.mjs` converts evaluated IR to SVG path data. It scales each path from its declared
coordinate system into the shape extent, emits all six DrawingML command kinds, converts visual
angles for non-circular ellipses, preserves negative sweeps, and splits full circles so SVG does
not collapse equal endpoints. Intermediate calculations retain binary64 precision; coordinates
are rounded to six decimal places only when serialized.

`geometry:check` now evaluates and emits all 319 paths for all 186 shapes at 216x216, 400x180,
and 180x400. It rejects empty or non-finite output and fingerprints each complete profile. These
gates prove deterministic emission, not visual equivalence with PowerPoint.

## Preset text rectangles

The same generated runtime module also carries all 181 standard text rectangles with only their
required adjustment/calculated guides. This projection is independent of the geometry path rollout.
Guide dependency pruning preserves source order and rebinding when a guide name is assigned twice.
`getOoxmlPresetTextRectangle()` evaluates those bounds in the current shape's pixel space; the shape
renderer uses them for text layout while preserving explicit `txXfrm` precedence and full-box defaults.

## Production subset

The runtime subset contains 20 native-validated single-path flowcharts and eight multi-path
flowcharts. The multi-path definitions have no adjustment guides and exactly three ordered paths:
the first carries the normal fill without a stroke, and later paths carry no fill while retaining
their declared detail/outline stroke flags. A 28-case native PowerPoint matrix checks every
flowchart definition at square and wide standalone extents plus a tall extent produced by a non-identity
group; explicit solid paint and theme style references are both represented.

`donut` is the adjustment-bearing production definition. Its contract pins
the single `adj` guide to the literal default `25000` and requires one polar radius handle with
literal bounds `0..50000`. The generated calculated guide retains the source `pin` formula, so
out-of-range overrides clamp according to the pinned definition. Runtime/build-time parity covers
`0`, `1`, `25000`, `49999`, and `50000` at square, wide, and tall extents.

Runtime generation requires every candidate to declare its expected path count. Multi-path
candidates must also pin the exact per-path `fill`, `stroke`, and `extrusionOk` tuple. A candidate
with adjustments must pin the exact ordered guide names, literal defaults, handle kind/axis, and
literal bounds. The gate rejects missing names, duplicates, uncontracted adjustments, count
mismatches, and any contract drift, so an unsupported definition cannot enter production by editing
the name list alone. The renderer
applies theme line paint and dash/cap/join attributes to each declared stroke, keeps detail paths
above image fills, and clips pictures to the first fill-bearing path. Expanding the subset still
requires formula/IR parity, SVG, parent-renderer, browser,
picture-clip, and current native PowerPoint oracle evidence for every new shape or family.
Renderer-owned theme fill, masks, markers, effects, and resource lifecycle remain outside the
geometry engine.
